# Printing categories and status emails

Hackers choose Hackathon project or Personal print for each new request. Hackathon project means a part used in their hackathon project. Project requests take priority over other waiting prints; jobs already printing are not interrupted. Within each priority group, original submission order is preserved. Existing requests remain uncategorized until the hacker or an organizer chooses; they are not automatically called personal.

Checked-in hackers can categorize their own received or needs-clarification requests, even while submissions are closed. Organizers can correct these categories. Both views show category and explain project priority. Completed and printing requests cannot be reclassified.

Submissions, category changes, cancellations, organizer status/note changes, and manual timing changes all send updates. Replayed and unchanged saves do not send again. The dashboard shows saved status/category/notes and only explicit organizer timing.

Status and reminder emails use the existing Knight Hacks IX arrival email artwork, navy/purple palette, serif typography, and yellow action button. Prominently display the Shinies wordmark above the message heading and name Shinies as the printing partner in text, including the plain-text email. Include status, description, category, organizer note, and tracker link. Do not promise automatic print times. Keep non-IX emails event-neutral.

The user selected sending one reminder after launch, not an organizer send button. Send one email per recipient with eligible uncategorized requests, linking to the category editor. Exclude printing, completed, cancelled, and categorized requests. Never reset status or submission time.

## Session limits, materials, and queue clarity

Show the Shinies inventory for Knight Hacks IX: black PLA, black PETG, white PLA, transparent PETG, pink PLA, brown PLA, silver silk PLA, and gold silk PLA. Hackers specify their preferred filament in the existing print description. State that sessions are limited to one hour so everyone has a chance; oversized requests may be cancelled. This is a maximum, not a fixed duration for every model.

Show the hackathon-project and personal queues with their counts. Show the active project and personal totals (for example, “10 hackathon projects · 5 personal prints”) above the queue. Each waiting request shows its overall place in line. Explain that projects have priority, running prints finish first, and new project requests can move personal prints back. Uncategorized legacy requests remain clearly labeled. Needs-clarification requests are on hold and do not have a queue position until an organizer returns them to Received.

Replace the organizer's exact-date/time control with a duration entered in hours and minutes (for example, 1 hour 30 minutes). Longer-than-one-hour estimates are allowed for accurate organizer planning, with a visible session-limit warning. Entering Printing starts the timer using the server's time. Editing the duration of a running print recalculates from its original start; note edits and repeated saves never restart it. Both dashboards show a live countdown and approximate finish time. An expired estimate does not automatically mark a print ready; organizers still confirm completion and pickup. Status, note, and timer changes continue to send the existing branded email updates.
